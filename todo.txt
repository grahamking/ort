GPT 5.6 Terra list of unnecessary allocations or copies:

3. **The extensions buffer is copied into the ClientHello body**
   - **Location:** `src/net/tls.rs:162, 260–261`
   - `exts` is a separately allocated vector and its complete contents are copied into `ch_body`.
   - Building extensions directly in `ch_body` (with an extensions-length placeholder) would avoid this allocation and full copy.

4. **The ClientHello body is copied into a separate handshake-message buffer**
   - **Location:** `src/net/tls.rs:272–280`
   - `client_hello_body()` creates `ch_body`; `client_hello_msg()` then allocates `ch_msg` and copies `ch_body` into it.
   - The handshake header can be reserved/written in the original buffer, or the body can be built after a four-byte prefix, avoiding `ch_body`’s separate allocation and its copy.

5. **Every encrypted outgoing record uses two heap buffers and copies plaintext**
   - **Location:** `src/net/tls.rs:862–894`
   - `plain` is allocated and populated by copying `inner` plus one content-type byte (`872–874`).
   - `aes_128_gcm_encrypt(...)` then returns another allocated `out` (`886`).
   - Since TLS writes are chunked to at most 16 KiB, this is a significant per-record cost. An in-place encryption API or one reusable scratch buffer would remove one allocation and copy; accepting/appending directly into an output buffer could remove both transient buffers.

6. **Decrypted plaintext is copied into `TlsStream::rbuf`, then copied again to the caller**
   - **Location:** `src/net/tls.rs:740–810`, especially `800–805`
   - `read_record_cipher()` produces an owned `plaintext` vector. It is copied into `self.rbuf`, then the requested prefix is copied to `out`.
   - When the caller’s output buffer can hold the record plaintext, it could be copied directly from `plaintext` to `out`; only an unread remainder needs retaining. More broadly, reusing `rbuf` as the decryption destination would eliminate the intermediate decrypted-record allocation/copy.

7. **Alert reporting allocates unnecessarily**
   - **Location:** `src/net/tls.rs:779`
   - `level.to_string() + " alert: "` allocates a Rust `String`, and `CString::new(...)` allocates again.
   - The values are fixed literals (`"warning"`, `"fatal"`, `"unknown"`), so static NUL-terminated strings or direct writes would avoid both allocations. This is only on the alert/error path, so it is not a hot-path concern.

8. **`hkdf_expand_label()` allocates an `info` vector for every label expansion**
   - **Location:** `src/net/tls.rs:85–95`
   - It uses a correctly sized `Vec`, so it should not reallocate, but each call still heap-allocates a small temporary buffer. The TLS handshake makes many such calls.
   - Given the bounded TLS 1.3 label/context sizes used here, a fixed stack buffer or an HKDF expansion interface that streams the label fields would avoid these allocations. This is not a copy of an already-built buffer, but it is repeated unnecessary heap allocation.

9. **Redundant array conversions after fixed-size HKDF expansion**
   - **Locations:** `src/net/tls.rs:574–593` and `643–657`
   - Calls such as `hkdf_expand_label::<16>(...).as_slice()[..16].try_into().unwrap()` create/copy another `[u8; 16]`, even though `hkdf_expand_label::<16>` already returns `[u8; 16]`. Likewise for 12-byte IVs. These are stack copies, not heap allocations, and are very small, but they are unnecessary.

--- Perf

Performance ideas for the prompt path of ort, ordered by expected gain.

10. Parse SSE and JSON directly from bytes instead of building `String`s and mini ASTs.
- The prompt path only really needs `delta.content`, `delta.reasoning`, and the final `usage.cost/provider/model`.
- Right now the code reads line-by-line into a `String`, parses a full `ChatCompletionsResponse`, allocates strings, then allocates more strings for `Response::Content` and `ThinkEvent::Content`.
- A specialized byte parser for `data:` lines can write content straight to stdout and to the last-writer buffer without intermediate objects.
- This is one of the bigger response-side wins after the TLS fixes.

14. Prefer direct syscalls and `writev`/`sendmsg` over hand-written assembler for libc replacement.
- Replacing a libc call with inline assembly that still performs the same syscall will not buy much.
- The real win is cutting the dynamic dependency and fusing operations, for example with `writev`/`sendmsg` for request/output batching.
- So if you spend time in the libc area, spend it on syscall ownership and call fusion, not on assembly wrappers for identical syscalls.

15. Start connect/TLS before finishing request construction if you keep any concurrency.
- Right now the request body is built inside `prompt_thread`, before DNS/connect/TLS.
- If you keep a threaded design, split it into "start resolve/connect/handshake immediately" and "build body in parallel", then join when it is time to send.
- This is a smaller win than the record-path fixes, but it is a free way to overlap CPU with network latency.

16. Improve connect strategy for multiple IPs.
- `connect(addrs)` is serial and returns on the first successful address, with no ranking by historical RTT.
- Cache the last-good IP and RTT, sort cached addresses by that RTT, or race a small number of nonblocking connects and use the first to finish.
- This is especially helpful once DNS is cached because the next bottleneck becomes "which IP did we choose".

22. Shrink handshake allocations with stack buffers where practical.
- `client_hello_body`, `client_hello_msg`, `hkdf_expand_label`, `send_client_finished`, and some handshake parsing still allocate several short-lived `Vec`s.
- These are cold-path allocations, so they rank below the app-data path, but they are still worth cleaning up because you care about both speed and binary size.
- Stack or scratch-buffer versions should be straightforward because the message sizes are known and small.

## Top 10 TODOs by Value

### 1. **Parse JSON error responses from OpenRouter** (`src/net/http.rs:295`)
**Value: Very High.** Currently when the API returns an error (e.g., "not a valid model ID"), `ort` just dumps the raw JSON blob as a string. Parsing it to extract the `message` and `code` fields would give users clear, actionable error messages instead of opaque JSON dumps. Low effort, immediate UX improvement for every error case.

### 5. **Handle multiple parallel tool calls in agent mode** (`src/input/agent.rs:224`)
**Value: Very High.** LLMs increasingly emit multiple independent tool calls in a single response. If `ort` only processes the first one, the agent loop wastes a round-trip for each independent call. Supporting parallel returns would make agent mode significantly faster and more correct.

### 6. **Support non-PDF files (or restrict `-f` to PDF)** (`src/input/to_json.rs:415`)
**Value: High.** File attachments currently hardcode `data:application/pdf;base64` — sending any other file type as PDF will confuse the model. Either expanding to detect MIME types or explicitly restricting to PDF would prevent subtle failures. The more flexible approach (MIME detection) would unlock images, code files, etc.

### 8. **Store files in `last.json` so resume works with file attachments** (`src/common/data.rs:394`)
**Value: High.** When you resume a conversation with `ort`, file attachments are lost because they're not persisted in the last-state file. This means you can't use `-` (resume) after attaching files, which is a broken UX path. Storing base64 data in `last.json` would be straightforward if files are small, or storing file paths for larger ones.

### 9. **Support tool parameter arrays** (`src/input/to_json.rs:292`)
**Value: High.** Tool schemas can have `type: "array"` parameters, which need `"items": {...}` in the JSON schema. Without this, any tool with an array parameter (e.g., `list_files(["dir1", "dir2"])`) can't generate correct schemas. Blocks agent tooling capabilities.
